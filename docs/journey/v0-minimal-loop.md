# v0 演进笔记:单文件最小闭环

- 日期:2026-10-20
- 对应交付:`sproutcode.py`(195 行):DeepSeek 非流式客户端 + Agent 循环 + `read_file` / `write_file` / `run_shell` 三工具 + REPL
- 对照:无——**v0 是项目基线,无上一 tag**。本篇记录的是"从零到一"的第一步,后续每个版本的演进笔记都以这里为对照起点。

> v0 要回答的问题:不借助任何 Agent 框架,一个能用的终端 Coding Agent 最少需要什么。跑完这一版的答案:195 行 Python、一个 `openai` SDK 依赖、一个 while 循环。

## 改了什么

v0 之前,仓库里只有设计文档与实现计划;v0 之后,仓库里第一次有了能跑的 Agent。`sproutcode.py` 单文件 195 行,自上而下四段:

1. **配置与 Key 加载**(`load_api_key`):环境变量优先,兜底解析 `/root/.env` 中的 `DEEPSEEK_API_KEY=...` 一行;Key 只从这两个来源读,永不入库。
2. **三个工具 + 手写 JSON Schema**:`read_file` 读全文;`write_file` 整体覆盖写,父目录不存在时自动创建;`run_shell` 执行命令并返回退出码与输出,60 秒超时防卡死。Schema 本版手写,`@tool` 装饰器自动生成是 v1 的主题。
3. **Agent 循环**(`run_agent`,项目的心脏):LLM 与工具交替——模型发起 `tool_calls` 就逐个执行、结果以 `role=tool` 消息回传、再次调用 LLM,直到模型不再发起工具调用;单任务轮数上限 25,超限终止并提示拆小任务。
4. **REPL**(`main`):`/exit` 退出;API 报错与 Ctrl+C 都只丢弃本轮输入继续会话,不崩进程。

两条横切约定,后续所有版本继承:

- 工具结果统一 `(content, is_error)` 二元组,异常不向上抛,转成错误文本回传模型;
- 客户端走 OpenAI 兼容协议指向 DeepSeek,`max_retries=3`;换模型只改 `BASE_URL` / `MODEL` 两个常量。

刻意不做的事(各自留给对应版本):不拆包、不流式、不写 pytest(v1),不落会话(v2),不做审批与路径限制(v3)。

真机验收(2026-10-20,管道喂两轮输入,全程不退出 REPL):第一轮让 Agent 在 `sprout-demo/` 下创建 `hello.txt`,第二轮让它 `cat` 确认内容并 `ls` 目录。验收四条逐项通过:会话不崩、文件内容正确、终端能看到 `write_file(...)` / `run_shell(...)` 工具轨迹、最终回复是中文总结。

## 为什么

**为什么第一步是单文件裸写,而不是先搭包结构。** 设计文档 §3 的顺序依据是"先懂循环本质(v0)再谈架构(v1)"。Agent 的心脏是 tool calling 循环,用框架的话这一层正好被遮住;单文件裸写一遍,LLM 怎么发起调用、工具结果怎么回传、消息历史怎么维护,每一处细节都是自己处理过的。之后 v1 拆包时,才知道每个模块在保护什么——没有这段裸写,拆包只是目录美学。

**为什么刻意非流式。** 非流式响应里 `tool_calls` 是现成聚合好的对象,拿来就能用;流式要处理 SSE delta 的文本增量与 tool_calls 增量解析,同时引入体验和正确性两重复杂度。v0 只要正确性,先让循环跑对;流式是 v1 的事。

**为什么 Schema 手写。** 3 个工具手写 Schema 只有几十行,自动生成省不了什么;`@tool` 从签名 + docstring 生成 Schema 的收益,要等工具数量上来才成立。v1 再引入,那时"新增工具零样板"是真实动机,不是提前设计。

**为什么 25 轮上限和 `(content, is_error)` 现在就上。** 这两个是循环能跑的前提,不是提前做了 v3 的事:没有轮数上限,模型陷入重复调用就停不下来,一直烧 token;没有错误回传,一次"文件不存在"就把整轮会话掀翻。v3 的安全(审批、路径限制、输出截断)是另一层,那时再做。

**为什么验收用管道喂输入而不是交互式敲。** `printf '...' | .venv/bin/python sproutcode.py` 可复现、可留档,并且直接证明了验收标准里"全程不退出 REPL"这一条。

## 踩坑与收获

**1. `tool_call_id` 必须一一对应,否则下一轮直接 400。** 带 `tool_calls` 的 assistant 消息必须原样入历史,且每个 call 都要有对应的 `role=tool` 消息、`tool_call_id` 逐个对上;漏一个或少回一个,下一次请求就被服务端以 400 拒掉。代码里有两处都是为它服务的:`messages.append(msg)` 不做任何加工;Ctrl+C 中断时 `del messages[task_start:]` 把本轮输入连同半截 tool_calls 一起回退——半截历史留在 messages 里,下一轮必 400。收获:tool calling 的"多轮"不是模型自己记着的,全靠我们维护 messages 的结构完整性;Agent 状态就是这份消息列表,列表坏了 Agent 就坏了。

**2. 错误回传促自我纠正。** `execute_tool` 把所有异常兜成 `[ERROR] ...` 文本回传模型,系统提示词里也只有一句"工具报错时读错误信息,调整参数或命令后重试",并没有复杂的重试编排。实测模型确实会读着错误改参数重试。另一个容易混的边界:命令非零退出码不是 error——`run_shell` 返回 `exit 3` 是合法结果,只有真正的异常才算 `is_error`,这个区分在离线自检里专门断言过。收获:Agent 的纠错能力一半来自"错误也是模型可读的输入",把异常变成文本比把异常抛给人更好用。

**3. Agent 本质是 while 循环。** 跑通之后回头看,`run_agent` 核心就是一个循环:调 LLM → 有 `tool_calls` 就执行回传、再来一轮,没有就返回文本。没有任何魔法。Claude Code 这类产品在这一层的增值是工程化——流式、上下文管理、安全、产品体验——而不是循环本身。想明白这一点,后面每个版本做的事情都可以概括成"往这个循环的某个环节上加工程约束"。

**4. "勘察→动手→验证"是模型自发形成的,提示词没教。** 验收实录:第一轮收到"在 sprout-demo/ 下创建 hello.txt",Agent 先自发调 `run_shell`(`ls -la; ls -la sprout-demo 2>/dev/null`)勘察目录,确认环境后才 `write_file` 写入,最后再 `run_shell`(`ls -l ... && cat ...`)验证自己的产出——完整的"勘察→动手→验证"链路,而系统提示词只写了"动手优先、报错重试"。第二轮任务(确认内容 + ls)它就直接一条 `cat ...; echo "---"; ls ...` 完成,不再勘察。两轮各 1~3 次工具调用,25 轮上限远未触顶。收获:行为模式主要来自模型能力和给它的工具面,提示词只需要定方向;同时别高估任务对轮数的需求,轮数上限是保险丝,不是常态工况,不值得为它调参。

**5. `write_file` 自动建父目录,第一轮就用上了。** `os.makedirs(parent, exist_ok=True)` 三行代码:验收时 `sprout-demo/` 原本不存在,写入一步到位,省掉了"目录不存在→报错→mkdir→重写"一整轮往返。收获:把可预见的失败前置消化成工具内约定,能直接省掉 Agent 的重试轮次——省的是 token 和延迟;这类小设计在工具层做,比在提示词里教模型"先建目录"可靠得多。

**6. 非流式的体感,是 v1 流式输出的直接动机。** 每轮都要等模型完整生成完才有第一个字输出,任务执行中终端有明显停顿,`write_file` 参数一长尤其明显。这不是 bug,是 v0 的刻意选择,但真机用过一次就确认了:流式不只是观感问题,而是"Agent 现在在干什么"的可观测性——用户盯着黑屏时既不知道它在思考还是在写入。v1 上 SSE delta 聚合,动机来自这次体感,不是来自需求清单。

**7. 工具轨迹用 ANSI 暗色打印,过程可见但不抢戏。** 每次工具调用以暗色 `· write_file({...})` 打一行,参数超 60 字符截断;is_error 的结果再暗色回显一行。正文亮色、轨迹暗色,回看验收输出时一眼能分清"模型说的"和"模型做的"。注意截断只发生在打印层:完整参数照常执行、照常入历史。收获:终端 Agent 的可读性也是设计对象——过程信息要可见,但不能淹没模型的叙述;且展示层的裁剪不能泄漏进数据层。
