# v2 演进笔记:会话与上下文

对照 tag `v1` → `v2`。验收记录:54 个离线测试全绿;真机 resume 闭环(新进程凭记忆答出上一轮创建的文件与内容,未用工具);注入 600 token 小预算的暗号实验通过压缩后仍能召回早期关键信息。

## 改了什么

新增三个模块,`client.py`、`tools/`、`__main__.py` 零改动:

- `sessions.py`:会话 JSONL 落盘。一个会话一个文件,首行 meta(id/时间/模型/cwd),之后每条消息一行(`{"ts":…, "message":…}`);按**轮粒度**追加(一次 `agent.run` 成功后整轮写入);`SessionStore` 支持按 id 前缀打开(未命中/不唯一都报错)与按 mtime 列最近会话。目录在 `~/.sproutcode/sessions/`,不污染用户项目。
- `context.py`:token 近似计数(CJK ≈ 1 token、其余 ≈ 4 字符/token,对整条消息 `json.dumps` 后估算,键名与 tool_calls 开销一并近似)+ `ContextManager.maybe_compact`(估算超预算 70% 时,把 system 之后、最近 N 个 user 轮之前的旧块替换成一次无工具的 LLM 摘要调用,摘要以 user 消息注入;渲染旧块时单条截断 1500 字符)。
- `prompts/`:系统提示词与摘要指令外置为 `system.txt` / `compact.txt`,`importlib.resources` 加载,`config.SYSTEM_PROMPT` 常量删除。

既有模块的改动:

- `agent.py`:`run()` **起点**接压缩钩子;成功路径(含轮数上限收尾)触发 `on_turn_commit(本轮消息切片)`,异常/中断回退路径不触发——与 `task_start` 回退语义严格对齐,中断轮永远不落盘。
- `cli.py`:argparse `--resume <id前缀>`;斜杠命令 `/help` `/clear`(重置对话并开新会话文件,旧文件保留)`/resume`(无参列最近 10 条,有参切换并重放);banner 带会话 id;压缩发生时打暗色提示。
- 版本 0.1.0 → 0.2.0;测试 22 → 54 个。

## 为什么

- REPL 一关历史全丢,是 v1 的最大缺口;spec 把会话/上下文定为 Agent 区别于聊天机器人的分水岭。这一版之后,对话是可恢复的资产,上下文是受管理的资源。
- **文件 = 完整事实,压缩 = 内存视图**。会话文件从不改写,压缩只重构发给模型的消息列表。好处:resume 永远拿回完整对话(这正是验收标准);压缩策略可以独立演进(以后做摘要缓存也不影响落盘格式)。代价:恢复超长会话后首次 run 会重新摘要一次(多一次 API 调用),v2 接受这个取舍。
- 压缩检查放在 run **起点**而不是上一轮结束时:resume 重放出的超长历史天然被下次 run 收敛;且此时本轮 user 消息尚未入历史,摘要调用失败不影响 `task_start` 的回退语义——失败本轮整轮丢弃、可重试,和 v1 的错误路径完全一致。
- 提示词外置:提示词成了可 diff、可单独迭代的工件,调 prompt 不再动代码;`pyproject.toml` 配了 package-data,安装态也能读。

## 踩坑与收获

1. **压缩切口必须在 user 轮边界**。从倒数第 N 个 user 消息处切,旧块与保留块的边界天然落在"一轮对话"的起点,绝不会拆散 `assistant(tool_calls)`/`tool` 配对——悬空的 tool 消息会让下一次请求直接 400,v0 踩过的坑在压缩场景换了种面貌重现,结构化断言(每个 tool_call_id 都有配对)进了测试。
2. **"每轮检查"型钩子会反复触发,测试脚本要按次数推演**。计划自审阶段就栽过一次:超小预算(budget=10)下,第一次 run 后历史仍超预算,第二次 run 起点会**再次**压缩——行为完全正确,但测试给 FakeLLM 只备了两份脚本,第三份耗尽直接 AssertionError。修复是补足脚本;顺带确认了压缩会"滚雪球"(旧摘要并入下一轮旧块再次被摘要),v2 接受这种渐进信息衰减,摘要缓存留给后续版本。
3. **字符近似计数的取舍**。不引 tokenizer 换"除 openai SDK 外零依赖";误差用预算余量吸收(deepseek-chat 64K 窗口配 48K 预算、70% 阈值)。json.dumps 整条估算是个偷懒但有效的设计:role、键名、tool_calls 的 JSON 开销不用逐项特判,一把全近似进去。
4. **测试基建随被测行为一起长**。FakeLLM 的 requests 从裸 messages 列表改成 `{messages, tools}`——断言"摘要调用不带工具"必须能看到 tools 参数。改基建波及 3 处既有断言,一起更新。
5. **真机验收要排除假阳性**。"resume 后问上一轮做了什么"若不限制,模型可以 `ls` 现场发现文件,恢复失败也能答对——所以问题里明确"不要用工具,凭对话记忆回答"。压缩验收同理用"暗号实验"证明信息来自摘要而非原文(keep_recent=1,暗号轮早已不在原文窗口里)。
6. **验收脚本别把偶然写成必然**。JSONL 检查第一版把角色序列写死成"一次工具调用"的形态,而真机那轮模型实际调了两次工具(write_file + run_shell)——文件是对的,断言是错的。改成结构化校验(首行 meta、每行合法 JSON、无悬空 tool_call_id、resume 新轮追加在同一文件)后既鲁棒又更贴近要验证的本质。另:计划担心同秒创建的会话文件 mtime 排序抖动,实测 WSL2 纳秒精度不抖,预留的 os.utime 修补没用上,审查时删掉了预留 import——防御性代码也要有真实证据才留。
